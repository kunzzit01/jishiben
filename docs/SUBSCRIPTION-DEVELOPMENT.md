## 先运行模拟模式

1. 使用独立开发／测试环境，先备份数据库。API 启动时由 Flyway 执行新增 V13 迁移，不修改 V1–V12。
2. 在开发部署环境设置 `BILLING_MODE=SANDBOX`、`BILLING_SANDBOX_ALLOWED=true`、`BILLING_ADMIN_EMAIL=mingsoon249@gmail.com`。只改真实部署环境配置，不把密钥提交到 Git。
3. 构建 API 与 Web／App。Compose 已传递订阅配置。首次发布此版本时先维持功能锁定关闭，让老用户同步既有账本和计划。
4. 管理员使用 `mingsoon249@gmail.com` 登录。邮箱途径识别管理员时，服务器必须已经通过 Google 登录验证该邮箱并绑定 Google sub。仅用相同字符串注册普通密码账号不会获得管理员权限。另一个可用途径是运维确认身份后赋予数据库 ADMIN 角色，代码不会自动按邮箱提权。
5. 打开设置里的订阅行，在会员页的“订阅管理”打开模拟订阅、订阅申请。准备好测试用户后，再打开“锁定四项会员功能”。设置保存于数据库。
6. 游客无需注册记账账号，可直接选月付／年付并申请。已注册用户也使用同一个页面。此阶段仅提交模拟申请，不扣款。
7. 管理员刷新最近订阅／申请，对 PENDING 订单执行“模拟付款成功”，用户刷新后获得权益。
8. 管理员可模拟续费、取消续费、宽限期、扣款失败、暂停、恢复、到期、退款保留权益、退款并撤权。重复请求幂等，过时版本的事件会被拒绝并要求刷新。
9. 用户可取消模拟续费，当前已确认期限内保持会员；到期由服务端时间判断。关闭模拟开关会停止模拟权益，正式 Google 权益不依赖该开关。

模拟价为 RM8.90／月、RM79.90／年，仅用于开发展示，正式价格待产品确认。首版未实施 AI 次数计费／额度系统，不能把候选 100 次写成已交付能力。

## 游客、注册与恢复

服务端创建匿名 billing subject，返回随机 bearer 凭证，数据库仅存凭证摘要。游客凭证不具有普通账号数据 API 权限，也不是 Google 账号。客户端沿用现有会话存储方式保存游客凭证，不将凭证写入日志或 URL。

用户登录后，可在会员页主动确认把本机游客订阅绑定到当前账号。绑定后旧游客凭证失效，原购买标识保留为账号的关联身份。不会在切换账号时自动把会员转给另一人。

模拟游客身份在卸载或清除本机存储后无法恢复。正式 Google 购买可以由原 Google Play 账号重新查询和恢复。已绑定记账账号的购买需要登录原记账账号；未绑定的游客购买可以在新的游客安装身份恢复。恢复证明仍是服务器向 Google 验证后的购买，不信任客户端自报会员或金额。

## 正式 Google Play 模式

实际入口采用 Google Play Billing，由商店展示其在当前国家、账号和商品下支持的付款方式。App 不收集银行卡资料，也不自己实现每种支付渠道。

正式模式的前置项交给上架／运维负责人配合完成。

- 包名与构建一致，当前为 `com.kylim0103.jizhangapp`。
- 一个订阅商品 `premium`，普通自动续费 base plan 为 `monthly`、`yearly`，激活销售地区和最终价格。
- 上传包含 Billing 的原生 AAB 到测试渠道，配置许可证测试账号。普通测试渠道账号可能真实扣款。
- 启用 Google Play Developer API，给服务账号目标应用所需的财务数据、订单和订阅管理权限。
- 通过受支持的 ADC／只读服务账号文件提供服务器身份。可使用 `deploy/docker-compose.billing-google.yml` 挂载本地 `deploy/secrets/google-play-service-account.json`。该目录已被忽略，凭证文件必须让容器 app 用户可读，并限制主机访问。
- 设置 `BILLING_TOKEN_ENCRYPTION_KEY`，值为 32 字节随机密钥的 Base64 编码，用于 AES-GCM 加密购买 token。妥善备份，直接更换密钥会导致旧 token 无法解密，轮换需单独做迁移。
- 切换前关闭新申请与模拟开关；设置 `BILLING_MODE=GOOGLE_PLAY`、`BILLING_SANDBOX_ALLOWED=false`，正式环境始终关闭模拟入口。
- 配置 Pub/Sub topic、Google Play 官方发布者授权及认证 push。通知 URL 为 `https://正式API域名/api/premium/google/notifications`。
- `BILLING_PUSH_AUDIENCE` 必须匹配 push 的预期 audience，`BILLING_PUSH_EMAIL` 填用于认证推送的服务账号邮箱。通知入口验证 Google OIDC，与普通用户 JWT 分开。
- 发测试通知，完成真实许可证测试购买后，再由管理员开放订阅申请入口。恢复购买和合法已付款订单的校验不因关闭新申请而被阻断。

App 1.1.4 新增原生依赖 `expo-iap@6.4.3`，需要重建 Android 二进制。运行时按 appVersion 区分，避免旧 APK 误收需要新模块的 OTA。不要把此原生变更只作为旧 runtime 的 JS 更新发布。Expo Go／Web 可用于模拟测试，正式 Google 购买需要 Android 原生包。EAS 构建配置固定 Google 商店提供者。

## 已实现的购买规则

| 场景 | 处理 |
| --- | --- |
| 新购买 | 使用商店真实价格和对应 offerToken，附匿名化账号标识；服务端向 Google 验证包名、商品、base plan、状态与归属 |
| PENDING | 不授予新权益，不做购买确认；完成付款后重新验证 |
| 成功购买 | 先事务性持久化授权，再由独立后台步骤 acknowledge；网络失败会重试 |
| 取消续费 | 尚未到期继续有效 |
| 宽限期 | 依据 Google 返回状态和有效期继续权益 |
| Hold／已生效暂停 | 停止新的付费操作 |
| 到期 | 降级并保留免费能力和历史数据 |
| 退款／撤权 | 退款与撤权分别处理；正式状态重新向 Google 查询 |
| 重复提交、重复通知 | token 唯一约束和通知事件幂等 |
| 替换购买 | 处理 linkedPurchaseToken 并退役原授权，防止重复发放 |
| Play 外重新订阅 | 读取 outOfAppPurchaseContext 的原账号标识／过期 token 关联身份 |
| 恢复购买 | 重装、启动和回前台查询购买，服务端重验；已绑定其他账号时拒绝自动转移 |
| 通知延迟／乱序 | RTDN 仅触发向 Google 取最新状态，成功处理后记录事件再返回成功；失败交 Pub/Sub 重试 |
| 后台补查 | 单个受控调度，每批最多 20 条，外部请求超时与失败退避；新购买确认不会依赖 App 一直打开 |

Google 普通新订阅的购买确认窗口通常为 3 天，从完成付款开始计算。运维应监控未确认购买、连续验证失败和 Pub/Sub 重试／死信。当前日志和数据库记录提供排查基础，仍需按部署平台接入实际告警。后台恢复调度的验证应包含故障注入，而不只检查页面成功提示。

首版商品范围为普通月付／年付自动续费。未提供试用、促销、预付、分期、多商品组合、月年付主动切换 UI、地区替代计费、iOS 支付等功能。这些不是“所有 Google 产品功能已实现”的承诺；后续启用时需扩展解析、文案、状态与测试。平台支持哪些付款渠道，由 Play 和地区条件决定。

## 服务端权益与 OCR

服务端对新增额外账本、计划业务字段变更／重新开启、兑换财务字段变更分别校验权限。旧兑换的备注与凭证编辑、删除仍开放。同币种转账免费。客户端在确认会员失败时保留表单草稿，付费写入不擅自放行。

两份 nginx 配置在 `/ocr/` 加入订阅鉴权子请求，核验账号 JWT 或游客凭证，再进入 OCR 引擎。共享 OCR 密钥仍保留为额外校验。`/ocr/health` 保持开放。独立 OCR 引擎的端口应继续只对内部网络开放，不能绕过 nginx 暴露。

App 仅向与应用 API 同源的 OCR 请求附带记账凭证；自定义第三方 OCR 地址不会收到 App JWT 或游客凭证。独立部署 OCR 时必须为该入口部署相应可信鉴权，不能把共享密钥视为会员校验。

本地 OCR 仅能在 App 入口控制；受控服务器资源通过服务器权限控制。没有承诺让经过恶意修改的客户端无法运行它自己设备上的 OCR。

## 数据、隐私与运行注意

新增 `billing_subjects`、`billing_settings`、`billing_subscriptions`、`billing_events`。用户注销后外键解除个人账号关联，保留去标识化的购买、防重放及审计记录；正式隐私政策应明确需要保留的数据、用途和期限，并由负责人确定清理策略。删除记账账号不会自动取消 Google 的订阅，设置页的删除确认区已加入提示与会员中心入口，正式发布前验证这一流程。

订阅设置变更和模拟事件有审计记录。管理员页面展示最近 100 条，首版没有复杂搜索／分页后台。数据库更新使用事务、唯一约束和锁；大规模并发下需根据监控改为按订阅锁与队列，而不是假定已完成高并发压测。

公开游客创建端点应在实际网关设置限流，避免滥建匿名身份。本实现默认不放开任何付费入口，不包含线上网关限流的部署。
